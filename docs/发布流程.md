# 发布流程

> 一条命令产出 Android + iOS 全部构建物，并自动创建 GitHub Release。

---

## 工作流总览

仓库共三个工作流，职责严格分离：

| 工作流 | 触发方式 | 运行环境 | 产出 |
|--------|---------|---------|------|
| `build-android.yml` | 手动 / 改动 `native/android/**` / 被调用 | Linux | `libpikafish.so` 双 ABI + 插件包 |
| `build-ios.yml` | 手动 / 被调用 | **macOS** | `XiangqiEngine.framework` + 静态库 |
| `release.yml` | **打 tag** / 手动 | Linux（调度） | 聚合双端产物并发布 Release |

### 为什么这样拆

两个构建流都声明了 `workflow_call`，可被 `release.yml` 复用。
好处是**编译逻辑只有一份** —— 若把编译参数复制三份，改一处漏两处几乎是必然。

同时，**发布逻辑只存在于 `release.yml`**。
早期版本 `build-ios.yml` 自带 tag 触发和发布步骤，会导致同一个 tag
被两个工作流分别发布、产物互相覆盖，已修正。

---

## 发布一个版本

### 方式一：打 tag（推荐）

```bash
git tag v1.0.0
git push origin v1.0.0
```

自动执行：

```
verify（规则引擎测试）
   ↓ 通过才继续
├── android（Linux，双 ABI 矩阵）
└── ios（macOS，允许失败）
   ↓
release（聚合产物 → 创建 Release）
```

### 方式二：手动触发

Actions → **Release** → **Run workflow**，填入版本号（如 `v1.0.0-beta`），
可勾选「标记为预发布版本」。

## 关键设计说明

### 1. 发版前强制跑测试

`release.yml` 的第一个作业是 `verify`，跑规则引擎单测与端到端模拟。
**测试不过则整个发布中止**，避免发出带规则 bug 的版本。

### 2. iOS 允许失败，Android 不允许

```yaml
ios:
  continue-on-error: true
```

iOS 构建链路依赖 Xcode 环境，较易受 runner 镜像更新影响。
设计上：**Android 成功即可发版**，iOS 失败时 Release 说明中会明确标注
「iOS 产物本次构建失败」，而非静默缺失。

若 Android 失败，`notify-failure` 作业会输出错误并中止发布。

### 3. 产物聚合而非各自发布

`release` 作业用 `download-artifact` 收集所有构建产物，
统一打包后一次性创建 Release。这是避免产物覆盖的关键。

## Release 内容

每次发布包含 4 个文件：

| 文件 | 用途 | 体积 |
|------|------|------|
| `XiangqiEngine-android-release.zip` | **正式发布用**，仅 arm64 | 约 14MB |
| `XiangqiEngine-android-full.zip` | 含 x86_64 模拟器库，调试用 | 约 26MB |
| `XiangqiEngine-iOS.zip` | iOS framework + 静态库 + 权重 | 约 27MB |
| `xiangqi-app-source.zip` | uni-app 前端源码，可直接导入 HBuilderX | < 1MB |

> **选哪个 Android 包？**
> 上架用 `-release`（约 14MB，留足云打包 40MB 免费额度）；
> 需要在模拟器上调试才用 `-full`。

---

## 版本号规范

遵循语义化版本 `vMAJOR.MINOR.PATCH`：

- `v1.0.0` → 正式版
- `v1.1.0` → 新增功能（如残局模式）
- `v1.0.1` → 修复缺陷（如规则判定错误）
- `v1.0.0-beta.1` → 预发布，建议勾选 prerelease

## 常见问题

### Q：tag 推错了想重发

```bash
# 删除本地与远端 tag
git tag -d v1.0.0
git push origin :refs/tags/v1.0.0

# 到 GitHub Releases 页面手动删除对应 Release，然后重新打 tag
```

### Q：只想构建不想发布

直接运行 `Build Android Engine` 或 `Build iOS Engine`，
它们只上传 artifact（保留 30 天），不创建 Release。

### Q：`verify` 作业失败

说明规则引擎测试没过。本地复现：

```bash
npm test
# 或
node tests/test_rules.mjs
node tests/test_sim.mjs
```

### Q：iOS 构建失败怎么排查

Actions 页面点开 `ios` 作业，重点看：

1. **拉取源码 / 下载权重** —— 网络问题，重跑即可
2. **编译 iOS 静态库** —— 若报 `unsigned __int128` 相关错误，
   检查 `build_ios.sh` 中 `-DIS_64BIT` 是否存在（象棋 90 格棋盘必需）
3. **组装 framework** —— 检查符号校验，`pikafish_main` 缺失说明
   `engine_main.cpp` 未参与编译

### Q：Node 报 `MODULE_TYPELESS_PACKAGE_JSON` 警告

已修复。`app/package.json` 与根 `package.json` 均声明了 `"type": "module"`，
因为 `app/utils/*.js` 使用 ES module 语法。

注意 Node 是按**被导入文件最近的 package.json** 判定模块类型，
所以只在根目录声明是不够的，`app/` 下也必须声明。
