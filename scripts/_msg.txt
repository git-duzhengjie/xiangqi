fix(sound): 改为一次性实例，根治首次启动无声

老板一句话点破了七轮的方向错误：「与音频文件无关，因为关闭一次音效
再开启一次就正常了」。这句话直接排除了我此前全部的努力方向 ——
文件能播、路径正确、扬声器正常、音量正常、静音开关无关，
否则手动关开也不可能出声。

===== 逐行比对手动关开与 resetPipeline =====

手动关开（有效）：
  关 -> setEnabled(false) -> stopAll()
       销毁全部实例、pools = {}、ready = false，且不重建
  开 -> setEnabled(true)
       什么都不做，池子依然是空的
  用户下一次落子（距启动已十几秒）
       play() -> ensurePool() 现场创建实例 -> 立刻 play()
       实例创建即播放，寿命只有几毫秒

resetPipeline（无效）：
  清状态 -> preload() 立刻批量建好 12 个音效 x 2 = 24 个实例
  十几秒后落子 -> play() 复用早已创建好的实例
       实例已在池中闲置十几秒

差异不在路径、不在音频配置、也不在执行时机，而在【实例是否被复用】。
预先创建的 innerAudioContext 闲置十几秒后，其底层 MediaPlayer 已被
系统回收或退出可播状态，但 JS 对象仍在池中，于是 play() 静默失效：
不报错、不触发任何回调、audio_flinger 中没有 active track。

这与之前 adb 实测到的现象完全吻合，也解释了为什么我七次改路径都
无效 —— MediaPlayer 海量创建、全程零 error、0 active tracks，
根本不是路径打不开，而是实例已经失效。

===== 修改 =====

一、play() 改为一次性实例：每次播放现场新建，播完（ended / error /
    3 秒超时兜底）立即 destroy。这正是手动关开之后的行为模式，
    也是本项目唯一被真机验证过有效的模式。
    实例属性仍逐个独立 try，避免 obeyMuteSwitch 这类只读 getter
    赋值抛错导致整个实例被丢弃。
    保持不 stop()、不 seek() —— 新建实例仍在异步 prepare，
    seek 是非法调用会让播放器进入异常态；一次性实例天然从头播放。

二、preload() 不再预建实例，只做目录探测，避免首次落子时才开始
    探测而错过第一声。

三、删除 ensurePool 与 POOL_SIZE。它是本次故障的根源实现，
    改完后已无调用点，必须删掉，否则日后很容易被当作「性能优化」
    重新启用而再次踩坑。pools / cursor 字段保留，仅供
    stopAll / destroy / releasePools 的既有清理逻辑使用。

四、test-sound-timing.cjs 新增场景 5 专门覆盖实例生命周期：
    preload 未播放任何实例、play 时现场创建、播完立即销毁、
    第二次播放不复用旧实例、每次播放都新建。

    这里也补上了此前测试的盲区：原有 14 项断言全部通过却完全测不到
    本次故障，因为它们只检查路径与开关状态，从不检查实例生命周期。
    这正是我七轮都没定位到根因的原因之一。

    注：探测实例（probeDir 为每个候选各建一个）2 秒内即销毁、
    不参与播放，不属于预建，断言据此区分。

20 项断言全部通过。
