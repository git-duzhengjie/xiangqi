===== 六次失败的共同模式 =====

每次都基于某种理论断定「哪一种路径写法是对的」，然后全局只用那一种：

  第4版  自检面板在真机实测 file:// 能 canplay、裸绝对路径 MediaError
         → 全局改用 file://，仍无声
  第6版  解析 APK 发现资源在 assets 内部，推断绝对路径不存在
         → 全局改用相对路径 _www/，仍无声

第6版尤其危险：第4版毕竟拿到过 file:// 可播的正面实测结果，
我却凭 assets 的理论把它改掉了，很可能亲手毁掉了唯一可用的写法。

路径可用性取决于基座版本、Android 版本、资源是否被解压到应用私有
目录等多个变量，静态推理覆盖不了。停止猜测。

===== 本轮改法 =====

一、resolveSoundDir 改为 resolveSoundCandidates，返回候选列表：
      file:// + 换算后的绝对路径   （第4版唯一有正面实测的写法，排最前）
      裸绝对路径
      _www/static/sounds/          （基座相对路径）
      /static/sounds/
      static/sounds/
    自动去重并保持顺序。

二、新增 probeDir()：为每个候选各建一个临时 innerAudioContext，
    挂 canplay / error 回调，只赋 src 不调 play（避免多候选叠音），
    谁先 canplay 就锁定它并重建实例池，2 秒无人命中则放行并允许
    后续 resetPipeline 重新探测。

三、持久化只在真正出声后写入。
    canplay 仅代表解码就绪，不等于扬声器出声 —— 第4版曾出现
    canplay > play > ended 全部触发却依然无声。若在 canplay 时就
    写缓存，一旦记住某个能解码但不出声的写法，以后每次启动都会
    直接命中它并跳过探测，反而把问题永久锁死。
    因此新增 markDirWorking()，由正式播放链路的 onPlay 回调触发，
    只写一次；ensureDir 启动时优先读取该缓存以避免首声用错路径。

四、resetPipeline 同步清理 probing / probeDone / dirConfirmed /
    candidates，否则 App.vue 的三道保险重置时会因 probeDone 仍为
    true 而直接复用旧目录，得不到重新探测的机会。

五、test-sound-timing.cjs 断言按新语义重写：不再校验具体写法，
    改为校验机制本身（候选列表已生成、播放路径落在候选集合内、
    文件名正确、重置与开关行为正常）。14 项全部通过。
