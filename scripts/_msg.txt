fix(sound): 定位并修复无声真因——assets 内资源不能用文件系统绝对路径

同一个问题修了五次都没解决。这次按承诺上 adb 抓真机日志，拿到完整
证据链，确认前几次全都改错了方向。

===== 实测证据链 =====

1. logcat：MediaPlayer 被海量创建，AudioSystem 正常，全程零 error
2. dumpsys audio：STREAM_MUSIC 音量 30/100，Muted: false
3. dumpsys media.audio_flinger：2 Tracks of which 0 are active
   播放器在工作、音量正常、却没有任何音频数据被送去播放
4. 新增 scripts/check-apk-wav.cjs 手工解析 APK 中央目录（零依赖，
   含 zip64 兜底），12 个 WAV 全部存在且未压缩：
     assets/apps/__UNI__FDB861F/www/static/sounds/move.wav
     原始 5776 字节，STORED

===== 根因 =====

音效资源位于 APK 的 assets/ 内部。assets 是 APK（zip）里的条目，
不是文件系统上的独立文件。plus.io.convertLocalFileSystemURL
('_www/static/sounds/') 换算出的 /data/... 绝对路径在文件系统上
并不存在，加不加 file:// 前缀都打不开。播放器拿不到数据就静默
失败：不报错、不触发 error 回调、audio_flinger 中 0 active tracks。
这完整解释了此前所有现象。

更关键的是 ensureDir 的判定把优先级搞反了：

  const isFallback = newDir.indexOf('file://') !== 0 &&
                     newDir.indexOf('/data/') !== 0

它把打不开的 file:// 与 /data/ 视为「成功」，把基座真正能解析的
相对路径 '_www/static/sounds/' 视为「兜底」，于是每次 plus 就绪后
都主动把能用的路径替换成打不开的路径。

这也终于解释了「手动关一次音效再打开就有声」这个贯穿始终的线索：
那一瞬间实例是用相对路径重建的。我此前一直把它当成时序问题，
方向从一开始就错了。

===== 修改 =====

一、resolveSoundDir 直接返回基座相对路径，不再做任何换算
      APP-PLUS   '_www/static/sounds/'
      其他端     '/static/sounds/'

二、ensureDir 取消「真实路径 / 兜底路径」二分逻辑。相对路径始终
    可用，一次解析即可，无需重试升级。dirIsFallback 字段保留仅
    为兼容 preload / resetPipeline 的既有读取，恒为 false。

三、test-sound-timing.cjs 断言随根因修正而更新：
    从「必须是 file:// 绝对路径」改为「必须是 _www/ 相对路径，
    且不含 file:// 前缀、不是 /data/ 绝对路径」。
    13 项断言全部通过。

保留上一版的 resetPipeline 与 App.vue 三道保险。它们本身无害，
且能覆盖基座音频配置延迟生效的情况。
